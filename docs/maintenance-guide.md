# Maintenance Guide — 새 모델·핸드북 업데이트 시 수정 가이드

> **이 가이드의 트리거·영향 매핑·cadence는 모델 사이클 3회(v0.2.0 Opus 4.8, v0.4.0 Sonnet 5, v0.6.0 Opus 5) 표본 기준이다.** 트리거 분류·영향 파일은 그 실제 사이클들을 거쳐 보완됐다. cadence·임계값은 표본이 3회이며 모두 major "4주 이내" 창을 지켰다 — 다만 전부 수동 실행이라 분기 cadence 가설은 여전히 미검증이다(§7 참조). (v0.3.0은 모델 사이클이 아닌 콘텐츠 사이클, v0.5.0은 새 티어 재검토 사이클이라 cadence 표본에서 제외.)

## 0. 핵심 통찰 — 무엇이 자동으로 따라오고 무엇이 안 따라오는가

에이전트 frontmatter의 `model: opus / sonnet / haiku`는 **family alias**다. Claude Code가 현재 디폴트(Opus 5, Sonnet 5, Haiku 4.5; 2026년 7월 기준)로 자동 해석한다. **신모델이 나와도 `model` 별칭만으로는 에이전트 파일을 거의 건드릴 필요가 없다** — 단, 신기능을 채택하면(예: 아래 T5의 `effort` frontmatter 필드) 해당 에이전트 파일은 손대게 된다.

> **별칭 승격에는 Claude Code 최소 버전이 따라온다**(v0.6.0에서 관찰). `opus` → Opus 5는 **v2.1.219 이상**에서만 성립하고, 그 이전 버전에서는 같은 별칭이 4.8로 해석된다. 또 별칭 해석은 **제공자마다 다르다**(예: Microsoft Foundry의 `opus`는 아직 Opus 4.6). 즉 "별칭이라 자동"은 *같은 제공자 + 최신 CLI*라는 전제 위의 명제다 — T1 사이클마다 최소 버전과 제공자별 해석표를 확인해 핸드북 §3.1에 반영한다.

업데이트 부담은 주로 **버전·가격·effort·고유명을 명시한 텍스트**에 집중된다:
- `HANDBOOK.md` (§3 가격, §3.2 토크나이저, §4 effort, §3.1 모델 표)
- `docs/bootstrap-prompts/*.md` (사용법 줄 모델/effort, §2 배경 원칙, §5 에이전트 명세, §10 effort)
- `profiles/*/CLAUDE.md` (모델명 등장 부분)
- `README.md` (현재 버전·정책 문장, 경로 2 모델명, 상단 "최근 업데이트" 콜아웃)
- `CHANGELOG.md` (버전별 변경 이력 — 매 릴리즈 새 항목 추가)
- `profiles/standard/.claude/agents/{architect,deep-debugger,pr-reviewer}.md` (신기능 채택 시 — 예: Opus 에이전트의 `effort` 필드)

이 사실이 이 가이드의 실용적 토대다.

## 1. 업데이트 트리거 (어떤 일이 생겼을 때 업데이트하는가)

| ID | 트리거 | 예시 | 우선순위 |
|---|---|---|---|
| T1 | 같은 family의 신 모델 stable 출시 | Opus 4.8, Sonnet 5 | **major** |
| T2 | 모델 deprecation·sunset 공지 | Opus 4.6 sunset | **critical** |
| T3 | 새 effort 레벨 추가 | xhigh가 4.7에서 도입됐던 것처럼 | major |
| T4 | 가격·토크나이저 변경 | $/MTok 조정 또는 새 토크나이저 | major |
| T5 | Claude Code / sub-agent의 새 도구·feature | 서브에이전트 `effort` frontmatter 필드 공식화(v0.2.0에서 채택), `memory: project` 등 | minor |
| T6 | 핸드북 자체의 새 버전 발행 | 핸드북 §11에 새 비용 레버 추가 등 | minor~major |
| T7 | Anthropic 공식 best-practices 업데이트 | 모델 사용 권장값 변경 | minor |

### "지금은 업데이트하지 않는다" 신호 (anti-pattern)

- 모델이 **preview/beta**로 공개되었지만 stable이 아님
- 가격이 **한시적 프로모션**
- effort 레벨이 **베타 라벨**로 표시됨
- best-practices 글이 **draft·preview** 상태
- 단순 typo 수정 — 다음 minor에 묶어 처리

> **새 티어 메모(Fable 5 계기, 2026-06~07)**: T1은 *같은 family의 후속 모델*(Opus→Opus)을 가정한다. **기존 family 위의 새 티어**(예: Opus 위 **Fable 5**)는 이 표의 빈틈이다. 이때는 모델 별칭·에이전트 파일·effort 배정을 건드리지 말고, "상위 능력이 필요할 때 어느 레버를 쓰나(Opus effort↑ vs 상위 모델)"의 *의사결정 가이드*로 경량 추가한다(HANDBOOK §5.4). default를 바꾸는 같은-family 후속(T1)과 달리 **관망해도 잃는 효율이 0**이므로 cadence도 느슨해도 된다. v0.3.0→v0.5.0 왕복의 교훈 하나 추가 — **접근 정책(수출통제·플랜 편입)이 유동적인 시기에는 [Unreleased] 문서 추가로만 두고, 정책이 안정된 뒤(예: 플랜 정식 편입) 정식 minor로 승격한다.** 철회가 필요해져도 회수 비용이 0에 가깝다.

## 2. Cadence (언제 업데이트하는가)

| 우선순위 | 권장 cadence | 잠정값 근거 |
|---|---|---|
| critical (T2) | sunset 일자 **2주 전까지** 완료 | sunset 후에도 코드는 동작하지만 비용·정책 위험 |
| major (T1·T3·T4) | stable 출시 **4주 이내** | 너무 일찍 옮기면 회귀, 너무 늦으면 새 효율 못 누림 |
| minor (T5·T7) | **분기별 일괄** 처리 | 자잘한 변동을 매번 따라가면 캐시 무효화 부담 |
| 선택 (T6) | 핸드북 영향 범위에 따라 분류 후 위 규칙 적용 | — |

**cadence 임계값은 표본 3회(v0.2.0·v0.4.0·v0.6.0)에서 모두 지켜졌다** — major "4주 이내"는 잠정값에서 유지값으로 승격할 근거가 쌓였다. 다만 세 번 다 수동 실행이라 minor의 "분기별 일괄" 가설은 여전히 미검증이다 — §7 참조.

## 4. 업데이트 절차

```
1) Diff
   - 새 핸드북(또는 Anthropic 공지) ↔ 현재 HANDBOOK.md
   - diff를 §1 트리거 분류로 매핑

2) 수정
   - §3 영향 파일 매핑에 따라 파일 단위로 변경
   - shared/ 수정 시 ./scripts/sync.sh

3) 버전 결정 (README "버전 정책" 참조)
   - 호환성 깨짐 (필드 제거, 에이전트 삭제 등) → major (v0.1.0 → v1.0.0)
   - 큰 변경 (모델·가격·effort·새 에이전트 추가) → minor (v0.1.0 → v0.2.0)
   - 자잘한 문서 보완 → 다음 minor에 묶음

4) 버전 스탬프 갱신 (7곳) + 변경 이력
   - VERSION, HANDBOOK.md 첫 줄, README.md, 두 bootstrap-prompts, 두 CLAUDE.md
   - 일괄 치환: sed/grep으로 검증
   - grep -rn "v<NEW>" --include="*.md" --include=VERSION → 7개 파일에서 매칭 확인
   - CHANGELOG.md에 새 버전 항목 추가 (무엇을·왜) — 변경 이력의 단일 원천. README 상단 "최근 업데이트" 콜아웃과 HANDBOOK 말미 개정 노트도 갱신.
   - (CHANGELOG.md·이 가이드는 7곳 버전 스탬프 대상이 아님 — CHANGELOG는 누적 추가, 가이드는 자체 스탬프 없음)

5) 검증 A — 사이클 검증
   - ./scripts/sync.sh --check  → drift 없음
   - bootstrap prompts §3 트리 == profiles 실제 트리 (동일 검사 둘 다)
   - agents frontmatter에 inherit 0건
   - architect tools에 Edit/Write 미포함 (standard)
   - deep-debugger 본문에 "가설 3회" 명시 (standard)
   - `effort` 필드는 Opus 에이전트(architect/deep-debugger/pr-reviewer)에만, Sonnet/Haiku엔 없음
   - 직전 모델명 잔존 grep (예: 의도치 않은 직전 세대 권장값(예: "Opus 4.8") 0건)

5-2) 검증 B — 전체 문서 정합성 감사 (릴리즈 전 1회, v0.6.0에서 상설화)
   변경분만 보지 말고 저장소 전체를 여섯 축으로 훑는다. 여기서 나온 정정은 같은 릴리즈에 포함한다(별도 bump 없음).
   - B1 수치 전수 대조 — 가격·캐시 최소 프리픽스·컨텍스트/출력 한도·토크나이저 배수·effort 지원 레벨이 문서 전체에서 단일 값인가
   - B2 상호참조 유효성 — 모든 `§X.Y` 인용이 실제 절을 가리키는가, 목차가 실제 헤딩과 일치하는가
   - B3 카운트 표기 — "비용 레버 여덟 가지", "8개 에이전트", "워크플로우 4종" 등이 실제 항목 수와 맞는가
   - B4 stale 사실 전수 재검증 — 이번 사이클에서 건드리지 않은 절 포함, 모델·도구·Claude Code 기능 단정 문장을 현재 공식 문서와 대조
   - B5 문서 간 계약 — 부록 A ↔ bootstrap 본문, bootstrap §5 명세 ↔ agents 실제 frontmatter, shared/ ↔ profiles/, README ↔ README.en.md 정책, CHANGELOG ↔ 실제 diff
     · **sync 비대상 파일의 내용 드리프트**를 반드시 포함할 것 — `profiles/*/CLAUDE.md`, `shared/claude-md-common.md`, 두 라우팅 `SKILL.md`은 `sync.sh`의 의도적 제외 대상이라 `--check`가 통과해도 내용이 어긋날 수 있다. 핸드북에서 사실을 정정했으면 이 다섯 파일에 같은 사실이 있는지 grep한다(v0.6.0에서 실제로 놓쳤던 경로).
   - B6 시점 스탬프 — "2026년 N월 기준" 류가 여전히 유효한 서술에만 붙어 있는가

   왜 상설화했나: v0.6.0 감사에서 캐시 최소 토큰의 **자기모순**(같은 문서 두 곳이 다른 값), fast mode 지원 범위 stale, 공식 인용문 변경(35% → 30%)이 한꺼번에 발견됐다. 모두 "이번 변경분"이 아니라 이전 사이클이 남긴 부채였다 — 변경분 검증만으로는 잡히지 않는다.

6) (선택) 부트스트랩 동등성 테스트
   - 빈 디렉토리에서 docs/bootstrap-prompts/standard.md를 Opus에 실행
   - 결과를 profiles/standard/와 diff
   - frontmatter·도구·model은 정확 일치, 본문 문장 차이는 수용
```

## 5. 버전 부여 예시 (감을 잡기 위한 케이스)

| 변경 | 버전 |
|---|---|
| 핸드북 §3 모델 표에 Opus 4.8 1행 추가, bootstrap §10 effort 권장값 갱신 | minor (v0.1.0 → v0.2.0) ✅ 실제 적용 |
| 새 에이전트 `security-auditor` 추가 (도메인 특화, §14.2 가이드) | minor |
| architect `tools`에서 WebSearch 제거 (외부 영향) | **major** (호환성 깨짐) |
| 검증 강도 라우팅에 4번째 라벨 도입 (예: [Manual]) | minor |
| HANDBOOK.md typo 수정 1건 | 다음 minor에 묶음 (단독 bump 안 함) |
| 모델 deprecation에 따라 family alias 디폴트가 자동 변경됐을 뿐 | (Anthropic 측 변경) — 가격·effort 변동이 동반되면 minor |

### 5-1. Worked example — v0.2.0 (Opus 4.8) 실제 사이클

위 첫 행은 "모델 표에 행 추가"로 단순화돼 있지만, 실제 v0.2.0 작업은 **하나의 minor 안에 세 종류 변경이 묶인** 전형적 T1+T3+T5 복합 사이클이었다:

- **T1 (신 모델)**: 마스터·Opus 에이전트를 4.7 → 4.8로. 모델 표·매핑·CLAUDE.md·부트스트랩·README 모델명 갱신.
- **effort 디폴트 변경 (T1 동반)**: 4.8 기본값 high(4.7은 xhigh)에 맞춰 매트릭스·부트스트랩 권장 effort를 한 단계 하향.
- **T5 (신기능)**: `effort` frontmatter 필드 공식화 → Opus 에이전트 3개에 `effort` 채택. fast mode·dynamic workflows·대화중 system 항목을 핸드북에 편입.

교훈: 신 모델 출시는 보통 "모델명 치환" 하나가 아니라 **모델 + effort 디폴트 + 동반 신기능이 한 묶음**으로 온다. 한 번에 minor로 처리하되, §3 매핑을 트리거별로 모두 훑어 빠진 파일이 없게 한다.

## 6. 호환성 정책 — 기존 프로젝트는 자동 업데이트되지 않는다

복사 기반 워크플로우의 본질적 비용:
- `cp -r profiles/standard/. <new-project>/` 후, 그 프로젝트는 템플릿과 분리됨
- 템플릿 v0.2.0이 나와도 기존 프로젝트는 v0.1.0 그대로

기존 프로젝트가 새 버전 혜택을 받으려면 **세 가지 선택지**:
1. **수동 diff/merge** — `diff -r` 로 변경된 파일만 식별, 의도된 차이를 보존하면서 머지.
2. **선택적 복사** — 변경 영향 큰 파일만 (예: HANDBOOK.md, bootstrap-prompts) 덮어쓰기.
3. **재 부트스트랩** — 새 버전의 `docs/bootstrap-prompts/standard.md`를 Opus 5에 실행 (Opus 호출 비용 발생).

신규 프로젝트는 항상 최신 템플릿을 받는다.

- **절차(§4)에 "변경 이력 갱신" 단계 추가** — 변경 이력을 `CHANGELOG.md`(단일 원천)로 분리하고 README 상단에 "최근 업데이트" 콜아웃을 두는 체계 도입.
- **§5 예시 보강** — "모델 표에 행 추가"는 실제론 더 넓은 작업(effort 하향 + effort 필드 채택 + 신규 레버)이었음 → §5-1 worked example 추가.

### 사이클 4 결과 — v0.6.0 (Opus 5 반영, 2026년 7월)

네 번째 사이클이자 **Opus family의 두 번째 T1**. 앞선 사이클들과 결이 다른 지점이 있었다:

- **cadence 표본 n=2 → n=3.** major "4주 이내"를 세 사이클 연속 지켰다. 임계값은 유지값으로 승격.
- **§0의 별칭 통찰이 세 번째로 성립** — `model: opus` 별칭만으로 8개 에이전트 파일이 한 줄도 안 바뀌었다. 다만 **전제 조건 두 개를 새로 발견**해 §0에 메모로 박았다: 별칭 승격에는 **Claude Code 최소 버전**(Opus 5는 v2.1.219+)이 필요하고, **제공자별로 해석이 다르다**(Foundry는 아직 4.6). "별칭이라 자동"은 무조건이 아니라 조건부 명제다.
- **새 관찰 — T1이 가격·토크나이저를 그대로 두고 *행동만* 바꿀 수 있다.** 사이클 2(Sonnet 5)는 토크나이저·thinking 기본값이 바뀌어 §3.2·§4를 건드렸지만, Opus 5는 **가격·토크나이저가 동일**해 비용 레이어가 통째로 무변경이었다. 대신 모델의 기본 행동 성향(자체 검증·위임 과다·장황함·범위 확장)이 바뀌어 **처음으로 운영 지침(§9.2·§12.9~§12.11)까지 영향 파일에 들어왔다.** 교훈: 사이클 2의 T1 체크리스트 항목("토크나이저가 바뀌는가 / thinking·effort 기본값이 바뀌는가")에 **"모델의 기본 행동 성향이 바뀌는가"**를 추가한다 — 이 축은 §3·§4가 아니라 §9·§12를 건드린다.
- **권장값이 역방향으로 바뀔 수 있다.** 4.7·4.8의 공식 effort 권장은 "코딩·에이전틱이면 xhigh에서 시작"이었으나 Opus 5는 "기본값 high에서 시작"이다. **신 모델이 항상 "더 높은 설정"을 요구하지 않는다** — 권장값은 방향을 가정하지 말고 매번 공식 문서에서 다시 읽는다.
- **전체 정합성 감사(§4-5-2)를 처음 수행**했고, 즉시 값을 했다. 발견: ① 캐시 최소 토큰의 **자기모순**(§5.4는 "Fable 2048·4.8 4096", §11.4는 "4.8 1,024" — 정답은 512/1,024), ② §1.3의 토크나이저 서술이 §3.2와 불일치, ③ fast mode 지원 범위 stale(4.7 제거·4.6 무시·Claude API 전용 누락), ④ 공식 인용문 변경(35% → 30%), ⑤ 존재하지 않는 절 참조(`§3.6`), ⑥ 시점 스탬프 stale(§4.5·§11.6 제목). **여섯 건 모두 이번 변경분이 아니라 이전 사이클이 남긴 부채**였다 — 변경분 검증만으로는 영원히 안 잡힌다. 이것이 감사를 상설 단계로 올린 이유다.
- **감사가 신기능도 발견했다.** 공식 sub-agents 문서 전수 대조에서 `maxTurns`(§12.6의 결정론적 가드), 서브에이전트 상한 세 가지(§9.2·§12.8), `memory` 세 스코프와 **"메모리를 켜면 Read·Write·Edit이 자동 활성화"**(§14.5 — 읽기 전용 에이전트 설계와 충돌하는 함정)를 확인해 반영했다. B4는 stale 사실을 잡는 축이지만, **놓친 기능을 줍는 축이기도 하다.**
- **에이전트 리뷰를 붙였고, 자체 감사가 놓친 것을 잡았다.** 커밋 후 관점을 분리한 리뷰어 3인(사실 검증 / 정합성 재감사 / 편집)을 병렬로 돌렸다. 지시에 **심각도 필터를 걸지 않고** "찾은 것을 확신도·심각도와 함께 전부 보고"하게 한 뒤 걸러냈다(§12.7의 원칙을 리뷰 자체에 적용). 교훈 셋:
  - **가장 큰 결함은 자체 감사가 못 잡았다.** §12.8의 "자식 서브에이전트를 만들 수 없다"는 **거짓**이었는데(공식: 기본 3계층 스폰 가능), B4에서 내가 훑은 범위 밖이었다. 독립된 리뷰어가 같은 축을 다시 도는 값이 여기서 나온다.
  - **SSOT만 고치면 끝이 아니다.** 그 거짓은 `profiles/{standard,lite}/CLAUDE.md`·`shared/claude-md-common.md`에도 있었고, 이 셋은 모두 `sync.sh`의 **의도적 제외 목록**이라 `--check`가 통과해도 잡히지 않는다. **B5(문서 간 계약)에 "sync 비대상 파일의 내용 드리프트"를 명시적 항목으로 추가한다.**
  - **수정이 새 결함을 만든다.** 리뷰어가 잡은 것 중 4건은 내가 1차 리뷰를 반영하며 새로 만든 불일치였다(한쪽 표현만 완화해 다른 쪽과 어긋남 등). **정정 후에는 그 정정이 건드린 사실이 등장하는 모든 위치를 다시 훑는다** — 부분 수정이 가장 흔한 재발 경로다.
  - **분량은 사실과 별개의 축이다.** 편집 관점 리뷰어의 총평은 **"사실은 맞게 고쳤지만 필요한 것의 두 배를 썼다"**였다 — 같은 사실을 네 개 절에 중복 서술하고(pr-reviewer의 Opus 5 메모), 절 주제를 벗어난 문단을 붙였다(§12.7의 생물학 분류기). **이 사이클이 문서화한 Opus 5의 성향(§12.10 장황·§12.11 범위 확장)이 그 문서를 쓰는 과정에서 그대로 재현된 것이다.** 교훈: 리뷰어 3인 중 **최소 1인은 사실이 아니라 분량·중복·구조만** 보게 한다. 사실 검증만 돌리면 *정확하면서 두 배 긴* 문서가 남는다. 3차 라운드는 삭감이 목표였고, 정본을 하나 정해(§6.4) 나머지를 포인터로 바꾸는 것이 가장 효율이 높았다.

### 다음 모델 사이클에서 검토할 것
- §2 cadence 임계값이 반복 운영에서도 맞는가? (표본 3 — 세 번 다 "4주 이내" 준수. 분기 cadence는 여전히 미검증.)
- 부트스트랩 동등성 테스트(§4-6)를 자동화할 가치가 있는가? 특히 `effort` 필드와 **Opus 5의 범위 확장 성향**(명세에 없는 파일 생성)까지 동등성 검사가 잡아내는가?
- 호환성 정책(§6)에 마이그레이션 스크립트를 더할 가치가 있는가?
- **정합성 감사(§4-5-2)의 자동화.** v0.6.0에서 수동으로 6축을 훑었는데, 최소 세 축은 스크립트로 뽑을 수 있다 — B1(수치 grep 후 값별 그룹핑), B2(`§X.Y` 인용 ↔ 실제 헤딩 존재 여부 루프), B3(카운트 표기 ↔ 실제 항목 수), B5(부록 A ↔ 부트스트랩 diff, bootstrap 명세 ↔ agent frontmatter 대조). `scripts/audit.sh`로 묶으면 매 릴리즈 비용이 크게 준다. B4(stale 사실)와 B6(시점 스탬프)은 판단이 필요해 수동으로 남는다.
